# Submission: a hard EDA task for code-executing LLMs

**Task:** design an exploratory data analysis task that an LLM with Python code execution solves only partially, and define a score in [0, 1] for its answer.

**Result:** a synthetic manufacturing dataset with a known data-generating process, a ten-question prompt covering the three EDA steps (describe the data, identify salient features, interpret them), and a deterministic partial-credit scorer. On the final dataset (**v5**), with the full prompt and pandas and statsmodels available, no run scores 1:

- **Sonnet 5.5, the LLM challenged:** mean **0.866**, range 0.78-0.98 over 5 runs (v4: 0.960).
- **Haiku 5.5:** **0.840** on the 3 runs that gave an answer, range 0.77-0.88. The other 2 runs used all 60 turns without a final answer and score 0, so the mean over 5 runs is 0.504.
- **Opus 5.5:** **0.985**, range 0.97-0.99 over 3 runs. It nearly solves the task, and it is the only model that found every quiet trap.

**What the scores say.** A single total mixes questions every model solves with questions almost none does. Grouped by what each question's trap demands, the same answers show three levels of skill (`outputs/runs/profile.md`, finished runs on v4 and v5):

| Model | Loud traps: detected and fixed | Estimate after detection (A4, C2, C3) | Quiet trap: no signal (frozen logger) |
|---|---|---|---|
| Haiku 5.5 | 0.97 | 0.71 | 0.00 (3 runs) |
| Sonnet 5.5 | 1.00 | 0.79 | 0.20 (5 runs) |
| Opus 5.5 | 1.00 | 0.92 | 1.00 (3 runs) |

Code-executing models reliably fix a problem that announces itself: a parser error, a `-1` sentinel, a step of several standard deviations. They are less reliable at estimating what they have found, and only the strongest model looks for a problem that nothing announces. The quiet traps are what separates the models, and since Opus found them in every run, they can be found from the data alone.

## The task in brief

A plastics injection-molding plant with 4 lines and about 3,000 batches over 9 months. The target is the batch defect rate. The model gets three CSV files and ten questions with a JSON answer format:

- **Describe (A1-A4):** unique batches, missing humidity readings, the overall defect rate and the median actual mold temperature.
- **Identify (B1-B3):** direct drivers of defects, leakage columns, and a regime change.
- **Interpret (C1-C3):** the best single supplier, the humidity optimum for one resin, and the defect rate under a stricter cleaning schedule.

20 traps are planted in the data (`docs/task_design.md`, section 4), among them duplicates, sentinels, °F on one line, Simpson's paradox, a U-shaped effect with r ≈ 0, leakage, a hidden driver in the maintenance log, a cycle time that mediates the supplier effect, one date format per line, a silent sensor offset next to a real process change, a change of QC detection on one line, and in v5 batch numbers that repeat across lines, a frozen humidity logger and cleanings missing from the log. Each trap breaks the answer to a question that does not name it. From v4 its clue has to be inferred from the data rather than read in a note, and from v5 the naive analysis gives no warning at all.

## Results and calibration history

| Stage | Setting | Score |
|---|---|---|
| Pilot 00 | Sonnet 5.5 in the app, **no code execution**, v1 | 0.652 (by eyeballing; two guessable answers were then removed) |
| Pilot 01 | Sonnet 5.5 in the app with code, v2 | 0.995 (every trap was a checklist item) |
| Pilot 02 | Sonnet 5.5 in the app with code, v3 | 0.872 (the app sandbox had no statsmodels) |
| Harness | `claude -p`, v3, 23 runs | Haiku 0.955, Sonnet 0.982, Opus 0.994; no trap hit |
| Harness | `claude -p`, v4, 23 runs | Haiku 0.879, Sonnet 0.960, Opus 0.969 |
| Harness | `claude -p`, **v5**, 13 runs | Sonnet **0.866**; Haiku **0.840** on 3 finished runs (0.504 with the 2 turn-limit runs); Opus **0.985** |

v3 → v4 was driven by the v3 transcripts. Models never checked date formats, held every column fixed in counterfactuals, and read every clue that was stated in a file. v4 moved the clues into the data. Ideas for new traps were also collected from five other LLMs and filtered by the same criteria (`docs/task_design.md`, section 7d).

v4 → v5 was driven by the v4 runs. The models found almost every v4 trap, because each clue was loud: a parser error, a phrase in the prompt, a step of several standard deviations. They lost points only where a detected problem had to be estimated. v5 added traps that give no signal (`docs/task_design.md`, section 7e).

**Where the v5 points are lost** (`outputs/runs/v5_seed42/summary.md`, plus the responses and code of each run):
- **A2, the frozen logger.** L2's humidity logger repeats one value for six weeks, 123 times in a row; no other line repeats a value more than twice. Every finished Haiku run and 4 of 5 Sonnet runs counted the blank and `-1` readings only. All 3 Opus runs and 1 Sonnet run found the stuck sensor.
- **C3, the unlogged cleanings.** Ten weeks of L4 cleanings are missing from the log. Every Opus run treated the gap as unlogged cleanings, like the reference. Of the Haiku and Sonnet runs only two mentioned the 69-day gap, and one of them still used it as logged. Other runs concluded that L4 has no cleaning effect or overstated the saving (one scored 0).
- **A4, the sensor offset (as in v4).** The trap answer was given in 2 of 5 Sonnet runs and 1 of 3 finished Haiku runs.
- **The turn limit.** Two Haiku runs spent all 60 turns exploring and gave no answer.
- **Found:** every finished run noticed that 37 batch numbers occur on two lines with different contents. The prompt says each line's MES terminal assigns the number, which made this clue louder than intended.

On v4 the losses were mostly estimation errors after detection: Opus estimated the L1 sensor offset at 6.2 °C instead of 8 in all 3 runs, because its control group included L3, which has a real temperature change of its own (`outputs/runs/v4_seed42/summary.md`).

## The measure

- **Weighted mean** of ten question scores; the weights are stored in the key. Describe 0.28, identify 0.34, interpret 0.38.
- **Numbers:** linear decay from the truth to the *naive* answer a hurried analyst would give, so falling into the trap scores 0.
- **Sets:** F1. **Category:** exact match. **Regime change:** the line acts as a gate, and the date gets linear credit within 30 days.
- **Counterfactual truths come from the data-generating process itself**, not from a model fit.
- **Properties are tested:** correct = 1, empty = 0, partial strictly between, monotone, and a malformed field costs only its own weight. The expert reference notebook (`reference/`) scores 0.984 on v5 (0.989 on v4).

## Why the numbers can be trusted

- **Known truth.** The data are synthetic, so every answer is exact, and `tests/` check on 10 seeds that each truth can be recovered from the published files alone.
- **Ablations.** Every trap has a switch. Common random numbers guarantee that switching one off changes only that trap. With all 20 traps off, Haiku 5.5 scores 0.971 over 5 runs, one of them exactly 1 (`outputs/runs/v5_seed42_notraps/`), against 0.840 on its finished runs with the traps.
- **Isolation.** Each `claude -p` run runs in an OS sandbox with no network, cannot read the repository or the answer key, and gets no memory, hooks or MCP servers. `python -m edabench.runner --check <model>` verifies this on the machine it runs on. An audit of the saved code and transcripts of every run finds no access to `eval/`, `docs/`, the answer key or the preflight canary. The answers agree: 4 of 5 Sonnet runs gave the trap value for A2 (226), not the truth (349).
- **Repeats.** Every model runs several times and the report gives the run-to-run sd. A single run of Sonnet could have scored 0.88 or 0.985.

## Beyond the four deliverables

- **Paper:** `paper/main.pdf`, a six-page write-up of the task, the measure and the results (LaTeX source `paper/main.tex`, builds on Overleaf).
- **Results explorer:** `docs/explorer.html` (v5) and `docs/explorer_v4.html` (v4), self-contained pages (open them in a browser, no install). It shows the score of every model on every question, how often each trap was hit, the failure findings with links to the runs behind them, the calibration history, and each run's answers next to the truth with its full response. Rebuild it with `make explorer`.
- **Datasheet:** `docs/datasheet.md` documents the dataset in the *Datasheets for Datasets* format: motivation, composition, the generating process, intended uses, contamination and versions.
- **CI:** `.github/workflows/ci.yml` runs the tests on every push. It also regenerates the data and the answer key and fails if a byte changes, and re-runs the reference notebook, which must still score at least 0.98.
- **A generator, not a fixed file:** any seed gives a fresh instance with the same structure, and every trap can be switched off on its own for ablations.
- **A reusable harness:** `edabench.runner` runs any `claude -p` model or OpenAI-compatible API in a sandbox, repeats runs, and records library versions. `--check` proves the isolation on the machine it runs on.
- **Evidence of fairness:** tests on 10 seeds show that every answer can be recovered from the published files alone. A red-team prompt (`docs/red_team_prompt.md`) collected trap ideas from five other LLMs.

## Known limitations

- **Opus nearly solves v5 (0.97-0.99).** v5 meets the requirement (a score strictly between 0 and 1) for every model, but for Opus only just, and my own target band of 0.3-0.7 is reached only on the hardest questions of the weaker models.
- **v5 has fewer runs than v4.** It was built and run in the last day: 5 runs each of Haiku and Sonnet, and 3 of Opus.
- **The A1 trap was louder than intended.** Every run found the batch numbers shared by two lines, so T18 costs no points; the prompt's remark about the MES terminal is a stronger clue than needed.
- **Haiku's turn-limit failures** measure the budget as much as the analysis. The 60-turn limit is the same for every version and model; two of five Haiku runs reached it on v5 and none on v4 (full prompt).
- **The C3 wording was fixed in v5.** On v4 two runs answered with the true-process rate (corrected for the weaker L3 inspection) rather than the recorded rate. v5 says the rate is computed from the recorded `defective_units`; the v4 runs keep the old wording.
- **One model family, as the task asks for one LLM.** I benchmarked three Claude 5.5 models of different sizes; other families may score differently. The harness also supports OpenAI-compatible APIs, but the free tiers I tried were too small for a fair comparison: Gemini allows 20 requests a day, and Groq fits gpt-oss-120b only with a trimmed context. A paid path is ready but not yet run: any OpenRouter model goes through the same tool loop, prompt and turn limit (`--model openrouter --model-id <slug>`, `docs/harness.md`).
- **The score depends on the environment as well as the model.** The same model scored 0.87 in the app without statsmodels and 0.98 in the CLI with it. Library versions are recorded in every run's `metadata.json`.
- **One seed** for model runs. The generator can produce fresh variants for contamination checks (`data/CANARY.txt`).

## Next steps

- **More quiet traps.** v5 showed that a trap with no signal is missed even by a model that finds every loud one. The next step is a second frozen or saturated reading on another question, and a quieter version of T18.
- **Sequence traps.** Add production timestamps and batch order, to support traps such as resin changeover and defects attributed to the previous batch.
- **Questions where the correct answer is "not identifiable from these data"**, with their own scoring.
- **A semi-synthetic variant on real data.** Inject the same traps into a public table (for example from Kaggle). The data-quality answers keep an exact key; the causal ones would need expert judgment, and popular datasets carry a contamination risk, because their EDA notebooks are public.
- **More model families**, on paid APIs with equal budgets (the OpenRouter entry in `configs/benchmark.yaml`), compared by the skill profile rather than the total.
- **Traps designed by another model family.** v5 was designed with help from Claude, so its traps may sit where Claude looks. Traps proposed by another family, each with generator code and a recoverability test like the existing ones, would show whether the benchmark favours its designer.
