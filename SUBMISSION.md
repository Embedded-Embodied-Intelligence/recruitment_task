# Submission: a hard EDA task for code-executing LLMs

**Task:** design an exploratory data analysis task that an LLM with Python code execution solves only partially, and define a score in [0, 1] for its answer.

**Result:** a synthetic manufacturing dataset with a known data-generating process, a ten-question prompt covering the three EDA steps (describe the data, identify salient features, interpret them), and a deterministic partial-credit scorer. On the final dataset (v4), with the full prompt, Claude models with pandas and statsmodels score **0.81-0.99** (Haiku 5.5: mean 0.879, Sonnet 5.5: 0.960, Opus 5.5: 0.969; 23 runs). No run scores 1. Every model loses points on questions where a detected problem must also be *estimated* correctly.

## The task in brief

A plastics injection-molding plant with 4 lines and about 3,000 batches over 9 months. The target is the batch defect rate. The model gets three CSV files and ten questions with a JSON answer format:

- **Describe (A1-A4):** unique batches, missing humidity readings, the overall defect rate and the median actual mold temperature.
- **Identify (B1-B3):** direct drivers of defects, leakage columns, and a regime change.
- **Interpret (C1-C3):** the best single supplier, the humidity optimum for one resin, and the defect rate under a stricter cleaning schedule.

17 traps are planted in the data (`docs/task_design.md`, section 4), among them duplicates, sentinels, °F on one line, Simpson's paradox, a U-shaped effect with r ≈ 0, leakage, a hidden driver in the maintenance log, a cycle time that mediates the supplier effect, one date format per line, a silent sensor offset next to a real process change, and a change of QC detection on one line. Each trap breaks the answer to a question that does not name it. From v4 its clue has to be inferred from the data rather than read in a note.

## Results and calibration history

| Stage | Setting | Score |
|---|---|---|
| Pilot 00 | Sonnet 5.5 in the app, **no code execution**, v1 | 0.652 (by eyeballing; two guessable answers were then removed) |
| Pilot 01 | Sonnet 5.5 in the app with code, v2 | 0.995 (every trap was a checklist item) |
| Pilot 02 | Sonnet 5.5 in the app with code, v3 | 0.872 (the app sandbox had no statsmodels) |
| Harness | `claude -p`, v3, 23 runs | Haiku 0.955, Sonnet 0.982, Opus 0.994; no trap hit |
| Harness | `claude -p`, **v4**, 23 runs | Haiku **0.879**, Sonnet **0.960**, Opus **0.969** |

v3 → v4 was driven by the v3 transcripts. Models never checked date formats, held every column fixed in counterfactuals, and read every clue that was stated in a file. v4 moved the clues into the data. Ideas for new traps were also collected from five other LLMs and filtered by the same criteria (`docs/task_design.md`, section 7d).

**Where the v4 points are lost** (`outputs/runs/v4_seed42/summary.md`, plus the responses and code of each run):
- **A4, the sensor offset (trap hit in 20-40 % of runs).** The models detect the L1 sensor step, but:
  - Opus estimated it at 6.2 °C instead of 8 in all 3 runs, because its control group included L3, which has a real temperature change of its own.
  - Sonnet reversed the direction of the correction in 2 of 10 runs.
  - Haiku left it uncorrected in 2 of 5 runs.
- **C2 and C3, precision.** The humidity optimum and the cleaning counterfactual are estimates, and their errors vary from run to run.
- **B3, the decoy.** One Haiku run reported the fall in recorded L3 defects, which was a change of QC detection, as the regime change.
- **Detected, but not missed:** per-line date formats, the QC change and the recipe mediator in C1 (23/23 correct). Their clues turned out to be loud: a parser error, a phrase in the prompt, and a step of several standard deviations.

## The measure

- **Weighted mean** of ten question scores; the weights are stored in the key. Describe 0.28, identify 0.34, interpret 0.38.
- **Numbers:** linear decay from the truth to the *naive* answer a hurried analyst would give, so falling into the trap scores 0.
- **Sets:** F1. **Category:** exact match. **Regime change:** the line acts as a gate, and the date gets linear credit within 30 days.
- **Counterfactual truths come from the data-generating process itself**, not from a model fit.
- **Properties are tested:** correct = 1, empty = 0, partial strictly between, monotone, and a malformed field costs only its own weight. The expert reference notebook (`reference/`) scores 0.989.

## Why the numbers can be trusted

- **Known truth.** The data are synthetic, so every answer is exact, and `tests/` check on 10 seeds that each truth can be recovered from the published files alone.
- **Ablations.** Every trap has a switch. Common random numbers guarantee that switching one off changes only that trap.
- **Isolation.** Each `claude -p` run runs in an OS sandbox with no network, cannot read the repository or the answer key, and gets no memory, hooks or MCP servers. `python -m edabench.runner --check <model>` verifies this on the machine it runs on.
- **Repeats.** Every model runs several times and the report gives the run-to-run sd. A single run of Sonnet could have scored 0.88 or 0.985.

## Known limitations

- **Strong models still score above 0.9.** v4 meets the requirement (a score strictly between 0 and 1) but not my own target band of 0.3-0.7.
- **C3 became ambiguous with the QC trap.** Two runs answered with the true-process rate (corrected for the weaker L3 inspection) rather than the recorded rate defined in A3, and scored 0. The key follows the prompt's definition. A clearer wording ("from the recorded `defective_units`, as in A3") is the fix for the next version. I kept v4 unchanged so that its 23 runs stay comparable.
- **Only one model family has been benchmarked.** The harness also supports OpenAI-compatible free APIs, but Gemini's free tier (20 requests a day) cannot fit one run, and the Groq runs of gpt-oss-120b were not finished in time.
- **The score depends on the environment as well as the model.** The same model scored 0.87 in the app without statsmodels and 0.98 in the CLI with it. Library versions are recorded in every run's `metadata.json`.
- **One seed** for model runs. The generator can produce fresh variants for contamination checks (`data/CANARY.txt`).

## Next steps

- **Quiet clues.** Make traps whose detection produces no signal, so the difficulty lies in estimation and the choice of method. v4 showed that this is where models fail.
- **Sequence traps.** Add production timestamps and batch order, to support traps such as resin changeover and defects attributed to the previous batch.
- **Questions where the correct answer is "not identifiable from these data"**, with their own scoring.
- **More model families**, on paid APIs with equal budgets.

## Reproduce

```bash
make install && make test          # 105+ tests: generator, traps, reference, scorer, harness
make data && make reference        # regenerate data/ and the answer key; expert notebook scores 0.989
python -m edabench.scorer outputs/runs/v4_seed42/claude-sonnet/full/run_05/response.md
python -m edabench.runner --check claude-haiku     # isolation preflight
python -m edabench.runner --model claude-sonnet --variant full --runs 5
python -m edabench.report outputs/runs/v4_seed42
```
